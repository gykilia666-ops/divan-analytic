# Стратегия тестирования

Состояние на 2026-11-06 и план закрытия пробелов. Дополняет docs/requirements.md §18 (стратегия) и docs/measurements.md.

## Принцип

Деньги и права живут в PostgreSQL, поэтому «середина» пирамиды здесь толще обычного: главные гарантии
(баланс = журнал, повтор без двойной выплаты, RLS) проверяются в самой БД, а не моками.

```text
            E2E (Playwright)        12 файлов, ~56 сценариев × desktop/360 px — только demo
       Интеграция (pg, параллельно)  4 файла — конкурентность приема, расчета, лимитов, инициализации
     pgTAP (SQL в транзакции)       13 файлов, ~420 проверок — инварианты, RLS, прямые RPC
  Unit (Vitest)                     33 файла, ~225 тестов — домен, разбор поставщика, безопасность
```

## Пробелы и план (по приоритету)

### 1. E2E connected: полный путь пользователя — сделано 2026-11-06

Сейчас весь e2e идет в demo, где прогнозы не принимаются. Цепочка «вход → псевдоним → прогноз → кошелек →
расчет → статистика» проверена только руками. GitHub OAuth автоматизировать не нужно: в тестах сессию создает
локальный Supabase (admin API), а cookie ставится тем же `@supabase/ssr`.

- Отдельный проект Playwright `connected` (порт 3300, `APP_DATA_MODE=connected`, `SPORTS_PROVIDER=fixtures`),
  запускается в CI job `database` после `db reset`, локально — в verify.ps1.
- Реализация: `tests/e2e-connected/support.ts` — пользователь создается `auth.admin.createUser`, токен доступа
  подписывается локальным JWT-секретом стенда (вход по почте выключен, как в production), сессия ставится через
  `setSession` того же `@supabase/ssr`. Только против `127.0.0.1`/`localhost` (проверка в `env.ts`).
- Сценарии:
  1. новый пользователь → страница выбора псевдонима → выбор → баланс 10 000;
  2. прогноз 100 на исход → баланс 9 900, запись «Списание за прогноз», прогноз в «Мои прогнозы»;
  3. повторное нажатие «Подтвердить» (двойной клик) → один прогноз, одно списание;
  4. итог матча в fixtures + два запуска задания с подменой времени подтверждения → «Выигрыш», баланс,
     статистика и место в рейтинге после 5 расчетов;
  5. удаление аккаунта → выход, вход снова создает новый аккаунт;
  6. обычный пользователь: `/admin` → 404, `POST /api/admin/sync` → 403.

```ts
test("прогноз списывает монеты один раз даже при двойном клике", async ({ page }) => {
  await loginAs(page, await createUserWithPseudonym("Тестовый Игрок"));
  await page.goto(`/matches/${openMatchId}`);
  await page.getByRole("radio", { name: /Победа хозяев/ }).check();
  await page.getByLabel("Сумма").fill("100");
  const confirm = page.getByRole("button", { name: "Подтвердить" });
  await Promise.all([confirm.click(), confirm.click()]);
  await expect(page.getByTestId("bet-placed")).toBeVisible();
  await page.goto("/my/wallet");
  await expect(page.getByTestId("wallet-balance")).toHaveText("9 900");
  await expect(page.getByTestId("wallet-entry").filter({ hasText: "Списание" })).toHaveCount(1);
});
```

### 2. Тесты HTTP-слоя маршрутов — сделано 2026-11-06

14 маршрутов; бизнес-логика проверена в БД, но не обертка: проверка Origin, вход, валидация, лимит тела,
перевод кодов БД в HTTP-статусы, `Cache-Control`. Ошибка здесь (например, пропущенная проверка Origin в новом
POST) не ловится ни pgTAP, ни demo-e2e.

- Таблица всех изменяющих маршрутов в одном тесте: без Origin → 403, чужой Origin → 403, без входа → 401,
  тело > лимита → 400, мусорный JSON → 400; для каждого — `Cache-Control: no-store`.
- Реализация: Vitest, вызов экспортированных `POST/DELETE` с `NextRequest`, `getCurrentUser`/Supabase — через
  `vi.mock`. Быстро и без БД.

```ts
const MUTATING = [
  ["POST", "/api/v1/bets", betsPost],
  ["POST", "/api/v1/me/pseudonym", pseudonymPost],
  ["DELETE", "/api/v1/me/account", accountDelete],
  ["POST", "/api/admin/sync", adminSyncPost],
  ["POST", "/api/admin/conflicts", conflictsPost],
] as const;

it.each(MUTATING)("%s %s: чужой Origin → 403 без обращения к БД", async (method, path, handler) => {
  const res = await handler(request(method, path, { origin: "https://evil.example" }));
  expect(res.status).toBe(403);
  expect(rpc).not.toHaveBeenCalled();
});
```

### 3. Миграции против production-схемы — средний

CI проверяет миграции только «с нуля». Перед `supabase db push --linked` — обязательный `--dry-run` и список
применяемых файлов в журнале; правило expand/contract уже в docs/deploy.md. Для рискованных миграций —
прогон на локальной копии production-данных (runbook: dump → restore → migration → pgTAP).

### 4. Smoke после деплоя — средний

`scripts/smoke-prod.mjs` (только чтение): `/api/health` 200, `/matches` 200 с CSP и без `x-powered-by`,
`/api/v1/matches` отдает матчи не старше 1 часа (иначе задание не работает), `/api/v1/leaderboard` 200,
`/admin` → 404 и `/api/admin/jobs` → 401 без входа, `/api/internal/jobs/sync` без секрета → 401.
Запуск вручную после каждого деплоя; позже — GitHub Action по событию `deployment_status`.

### 5. Покрытие unit — низкий, но дешевый

Подключить `@vitest/coverage-v8` и пороги в `vitest.config.ts`: `src/domain/**` и `src/lib/**` — 90 % строк
и ветвей, `src/server/**` — 70 %. Покрытие — сигнал о забытом коде, а не цель: SQL-логика им не измеряется.

### 6. Визуальные регрессии — низкий

Три страницы (`/`, `/matches`, `/leaderboard`) × две темы × два размера через `toHaveScreenshot` с маской
времени и отключенным параллаксом (`reducedMotion: "reduce"`). Эталоны обновлять осознанно; только в одном
проекте Playwright, чтобы не плодить флаки.

### 7. Регулярная проверка формата football-data — низкий

`scripts/probe-football-data.mjs` раз в неделю (scheduled GitHub Action с секретом) сравнивает форму ответа с
сохраненной; расхождение — issue, а не падение сборки.

## Что сознательно не тестируем

- Сам GitHub OAuth и экран согласия GitHub — внешняя система; проверяем свою часть (callback, safe redirect).
- Нагрузку выше профиля §14.1 на бесплатных тарифах — расход квот без пользы.
- Тривиальные компоненты без логики и код фреймворка.

## Правила

- Новая функция БД, меняющая деньги или права, — pgTAP с прямым вызовом от `anon`, `authenticated` и чужого
  пользователя.
- Новый изменяющий маршрут — строка в таблице теста маршрутов (п. 2).
- Исправленный баг — сначала падающий тест.
- Флаки не «лечатся» ретраями: в CI разрешен один повтор, но каждый повтор разбирается (trace в артефактах).
- Этап считается завершенным только после зеленого verify.ps1 и зеленого CI (docs/requirements.md §17).
