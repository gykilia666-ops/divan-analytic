## 1. Продукт и позиционирование

### 1.1. Название и идея

Рабочее название: «Диванный аналитик».

Портфолио-проект: учебный симулятор спортивных прогнозов на реальные футбольные матчи. В приложении используются собственные демонстрационные коэффициенты и виртуальные монеты без денежной стоимости.

Главная инженерная цель: показать законченную разработку — от интерфейса и SQL-транзакций до внешнего API, фонового расчета, тестов, наблюдаемости и деплоя на Vercel.

Не называть продукт настоящим букмекером или источником реальных букмекерских коэффициентов.

### 1.2. Основной пользовательский путь

1. Посетитель понимает назначение приложения на главной странице.
2. Смотрит предстоящие матчи.
3. Входит через GitHub.
4. Однократно получает 10 000 виртуальных монет.
5. Выбирает один исход одного матча.
6. Видит демонстрационный коэффициент, сумму и потенциальную выплату.
7. Подтверждает прогноз.
8. Видит списание в журнале и ожидающий прогноз в истории.
9. После подтверждения результата получает расчет.
10. Смотрит обновленные баланс, статистику и рейтинг.

### 1.3. Запреты

В приложении отсутствуют:
- реальные деньги, депозиты, платежные интеграции;
- покупка или вывод монет;
- обмен монет между пользователями;
- реальные призы;
- партнерские ссылки на букмекеров;
- обещания заработка или гарантированного выигрыша;
- маскировка демонстрационных коэффициентов под реальные;
- обещание настоящего спортивного live на задержанном бесплатном источнике.

Дисклеймер в интерфейсе:
«Учебный симулятор. Монеты не имеют денежной стоимости. Коэффициенты демонстрационные. Спортивные данные могут поступать с задержкой».

Дисклеймер и отсутствие платежей не объявлять универсальной юридической гарантией. При коммерциализации, реальных призах или изменении механики требуется отдельная проверка применимых требований и правил сервисов.

### 1.4. Тон и визуальная идея

Профессиональный спортивный интерфейс с умеренным юмором:
- «Монеты ненастоящие. Уверенность — настоящая».
- «Экспертность временно не подтверждена».
- «Аналитика уровня: смотрел обзор».
- «Прогноз не зашел. Футбол виноват».

Юмор не мешает пониманию ошибок, статусов, сумм и правил. Не высмеивать пользователя за проигрыш.

## 2. Архитектура

### 2.1. Целевая схема

```text
Браузер
  └─ Next.js на Vercel
       ├─ Server Components: публичные страницы
       ├─ Route Handlers: HTTP API и команды
       ├─ Supabase Auth: GitHub OAuth
       ├─ Supabase PostgreSQL: доменные данные и SQL-функции
       └─ football-data.org: серверная синхронизация

Supabase Cron + pg_net
  └─ POST /api/internal/jobs/sync на Vercel
       ├─ импорт матчей
       ├─ обновление статусов рынков
       ├─ подтверждение результатов
       ├─ пакетный расчет прогнозов
       └─ обновление статистики
```

Внешний API вызывается централизованной синхронизацией, а не при каждом открытии страницы. Браузер получает данные приложения, не токен поставщика.

### 2.2. Принципы serverless

- Не рассчитывать на постоянно работающий процесс.
- Не использовать память функции как общее состояние, lock или rate limiter.
- Не хранить важные данные в локальной файловой системе функции.
- Фоновые работы — короткие, ограниченные, возобновляемые пачки.
- Lease, cursors, rate limits и результаты хранятся в БД.
- Не удерживать SQL-транзакции во время HTTP-запросов.
- Сбой, повтор запроса или повтор запуска не должны удваивать операции.

### 2.3. Почему не отдельный backend

Next.js закрывает страницы и API в одном Vercel-проекте. PostgreSQL закрывает транзакционную доменную логику. Отдельные NestJS/FastAPI, Redis, Celery/BullMQ и постоянный worker не нужны для MVP и усложнили бы бесплатный деплой.

Не добавлять Kubernetes, Kafka, ClickHouse, микросервисы или собственный WebSocket-сервер ради портфолио. Не делать абсолютных заявлений о возможностях WebSocket на Vercel: архитектура MVP от них не зависит.

Перед реализацией проверить актуальные pricing, policies, доступные ресурсы и доступ конкретного токена. Если условия изменились — документировать изменение, не подключать платный тариф молча.

## 6. Функциональные требования

### 6.1. Роли

Гость: публичные матчи, рейтинг, правила, локальная демонстрация, вход. Не читает чужие приватные данные и не пишет прогнозы в общую БД.

Пользователь: собственные прогнозы, баланс, журнал, статистика; редактирование разрешенных полей профиля.

Администратор: статус заданий, ошибки, разрешенный ручной запуск, приостановка рынков, аудит и ограниченное восстановление. Роль хранится вне редактируемого пользователем профиля.

### 6.2. Авторизация

- GitHub OAuth через Supabase Auth.
- Callback и разрешенные redirect URLs для localhost/production.
- Возврат только на разрешенный внутренний маршрут.
- Выход завершает сессию.
- Сервер проверяет пользователя независимо от UI.
- Для SSR использовать актуальную схему Supabase getClaims/getUser; не доверять только данным getSession из непроверенного клиентского состояния.
- Команды дополнительно проверяют disabled_at в БД.
- Истекшая сессия дает понятный 401, не анонимное выполнение.

### 6.3. Профиль и кошелек

- UUID — идентификатор пользователя.
- display_name: 3–24 символа, безопасный текст.
- Одинаковые display_name разрешены.
- Аватар: проверенный OAuth URL либо локальный fallback.
- 10 000 монет начисляются однократно.
- Повторный callback и конкурентная инициализация не выдают дополнительное начисление.
- Инициализация профиля, кошелька и записи INITIAL_CREDIT — атомарная и идемпотентная процедура.

### 6.4. Матчи

Карточка: команды, соревнование, время, статус, коэффициенты, время синхронизации, предупреждение о задержке.

Фильтры: дата, соревнование, предстоящие/завершенные. Сортировка: kickoff_at и стабильный tie-breaker. Обязательны пагинация и состояния загрузки/пустоты/ошибки.

### 6.5. Даты и часовые пояса

- БД: timestamptz.
- Доменное время: часы PostgreSQL.
- UI: зона браузера с явным отображением и возможностью выбора.
- Проверить Asia/Krasnoyarsk.
- Дата фильтра означает сутки в выбранной зоне, преобразованные в UTC-интервал.
- Тесты не зависят от реальных сегодняшних дат.

### 6.6. Рынки

Единственный тип MVP: результат основного времени 1/X/2.

Статусы:
```text
OPEN -> SUSPENDED / CLOSED -> RESOLVED / VOID
```

Не считать схему исчерпывающей таблицей переходов: реализовать явный валидатор допустимых переходов. Терминальные состояния не переоткрываются автоматически.

Условия приема:
- OPEN;
- матч еще не начался;
- до старта больше 5 минут;
- данные не старше 60 минут;
- исход существует;
- quoteVersion совпадает;
- аккаунт активен;
- сумма и баланс допустимы.

Рынок закрывается по серверному времени независимо от задержанного статуса поставщика. Кубковые матчи с дополнительным временем исключить, пока не реализована однозначная интерпретация основного времени.

### 6.7. Купон

- Один матч и один исход.
- Целая сумма от 10 до 1 000 монет.
- Нельзя больше баланса.
- Один принятый прогноз пользователя на рынок.
- Отмена принятого прогноза пользователем отсутствует.
- Показывать коэффициент и потенциальную выплату с пояснением, что она включает поставленную сумму.
- Кнопка отправки блокируется на время запроса, но серверная идемпотентность обязательна независимо от кнопки.
- Локально сохранять только черновик выбора/суммы, не доверенный баланс.

Команда:
```json
{
  "marketId": "uuid",
  "outcome": "HOME",
  "stake": 100,
  "quoteVersion": 1,
  "idempotencyKey": "uuid"
}
```

Не доверять клиентским userId, payout, odds, balance, status или result. При смене quoteVersion вернуть 409 QUOTE_CHANGED и запросить повторное явное подтверждение.

### 6.8. История

Статусы: PENDING, WON, LOST, VOID.

Запись: матч, исход, stake, accepted_odds, potential_payout, actual_payout, даты создания/расчета. Cursor pagination, фильтры статусов. Только собственные записи.

### 6.9. Статистика

Показывать число рассчитанных прогнозов, выигрыши, win rate, сумму учитываемых ставок, чистый результат и ROI.

- В основной расчет входят WON и LOST.
- VOID не участвует в win rate и ROI.
- PENDING не участвует в завершенной статистике.
- INITIAL_CREDIT и ADMIN_ADJUSTMENT не являются игровой прибылью.
- profit = сумма выплат по WON/LOST минус сумма ставок по WON/LOST.
- ROI = profit / stakes * 100%.
- Win rate = WON / (WON + LOST) * 100%.
- Нулевой знаменатель: «—».

### 6.10. Рейтинг

По чистому игровому результату. Допуск: минимум 5 рассчитанных WON/LOST.

Сортировка: net_profit DESC, settled_count DESC, стабильный технический tie-breaker. Не ранжировать по балансу. Публиковать только разрешенный nickname/avatar и агрегаты; не email, внутренние роли или приватный журнал.

## 7. Демонстрационные коэффициенты

Коэффициенты — игровые воспроизводимые значения, не обученная модель и не реальный прогноз.

Алгоритм:
1. Взять стабильный внешний ID матча и model_version.
2. Детерминированно получить три положительных веса.
3. Нормализовать в вероятности pH + pD + pA = 1.
4. Ограничить вероятности алгоритмом, сохраняющим нормализацию.
5. Рассчитать odds_i = 1 / (p_i * 1.06).
6. Проверить диапазон 1.10–12.00.
7. При некорректном результате не открывать рынок.
8. Сохранить коэффициенты и версии в БД.

Важно:
- Не генерировать на клиенте и при каждом просмотре.
- Не использовать итог матча для генерации.
- Фиксировать коэффициенты при создании рынка в MVP.
- Один матч/версия модели -> один результат.
- Сохранять model_version и quote_version.

Представление: odds_milli, целое число; например 2350 = 2.350.

Выплата: floor(stake * odds_milli / 1000), включает исходную сумму. Расчет в PostgreSQL без JS floating point. Проверить границы, округление, допустимые числа и переполнение. Клиентский предварительный расчет — только отображение.

### 8.2. Инварианты

## 9. Команды, транзакции и конкурентность

### 9.1. place_bet

Реализовать PostgreSQL-функцию. Одна транзакция:
1. Определить auth.uid() либо эквивалентный проверенный контекст.
2. Проверить аккаунт и допустимость вызова.
3. Нормализовать команду и проверить idempotency key/request hash.
4. Получить блокировки в едином порядке.
5. Проверить рынок, матч, время, свежесть и quote version.
6. Проверить лимиты суммы и отсутствие другого прогноза на рынок.
7. Проверить баланс.
8. Создать bet.
9. Создать STAKE_DEBIT с уникальным operation_key.
10. Обновить wallet.
11. Вернуть сохраненный результат.

Внешние HTTP, отправка уведомлений и ожидание таймера внутри транзакции запрещены.

### 9.2. Идемпотентность

Повтор той же команды с тем же ключом возвращает исходный успешный результат, даже если рынок уже успел закрыться. Повтор ключа с другим содержимым -> 409 IDEMPOTENCY_CONFLICT.

Корректно обработать конкурентные одинаковые запросы, а не только последовательные. Использовать уникальные ограничения, request_hash и согласованную блокировку/обработку конфликта. Не перехватывать все ошибки как «успех».

Для нового намерения пользователь создает новый ключ; при сетевой неопределенности повторяет старый. Клиент не должен генерировать новый ключ на каждый retry той же операции.

### 9.3. Блокировки

Установить и документировать общий порядок, например market -> bet -> wallet. Реальные функции должны соблюдать его, включая payout, refund и административные операции. При блокировке нескольких сущностей сортировать ключи. Отдельно описать начальную инициализацию, где market отсутствует.

Не держать SQL-lock во время сетевых запросов. Защита от deadlock: порядок, короткие транзакции и ограниченный retry только для безопасно повторяемых команд.

### 9.4. Расчет

Расчет по сохраненному принятому коэффициенту, не текущему.
- WON: credit potential_payout.
- LOST: credit отсутствует; actual_payout = 0.
- VOID: credit stake.

Повторный расчет терминальной записи — no-op. Защита: обновление только PENDING и уникальный operation_key начисления. Состояние, журнал и wallet обновляются атомарно.

### 9.5. Коррекция результата

Если после расчета поставщик изменил результат:
- зафиксировать конфликт и аудит;
- не перезаписывать рассчитанные bets и балансы автоматически;
- приостановить дальнейшие неоднозначные действия;
- предоставить документированный ограниченный скрипт ручной проверки и компенсации;
- компенсация — новая запись журнала, а не редактирование истории.

Не пытаться решить ситуацию автоматическим списанием, создающим отрицательный баланс.

## 10. Интеграция и задания

### 10.1. Адаптер

```ts
interface SportsProvider {
  getCompetitions(): Promise<CompetitionDTO[]>;
  getMatches(input: MatchQuery): Promise<MatchDTO[]>;
}
```

Реализации: FootballDataProvider и FixtureSportsProvider.

Внешние DTO проверяются Zod. Доменные статусы не копируют непрозрачно внешние строки. Неоднозначность -> явное состояние, не угадывание.

Повторный импорт не создает дубликаты. Отсутствие матча в одном ответе не означает отмену. Старый provider_updated_at не должен перезаписывать более новое подтвержденное состояние без принятого правила.

### 10.2. Планирование

Supabase Cron каждые 15 минут вызывает POST на Vercel. HTTP выполняется через pg_net. Секрет хранится подходящим защищенным способом, например Vault, не в репозитории. Доступ к очередям запросов и секретам ограничен.

Отдельный CRON_SECRET, не service-role key. Cron не пересылает пользовательскую сессию. Production job включается только для production origin.

### 10.3. Pipeline

1. Проверить машинную аутентификацию.
2. Получить атомарный lease.
3. Записать job_run.
4. Проверить бюджет запросов и next_allowed_at.
5. Получить агрегированные данные с timeout.
6. Проверить и нормализовать.
7. Upsert.
8. Закрыть просроченные рынки.
9. Создать недостающие допустимые рынки.
10. Обновить подтверждения результата.
11. Рассчитать ограниченную пачку.
12. Обновить агрегаты и cursor.
13. Записать результаты/ошибки.
14. Освободить lease только владельцем.

Если HTTP недоступен/лимит исчерпан, выполнить доступную локальную работу: закрытие по времени и расчет уже подтвержденных результатов. Не блокировать все обслуживание только из-за пропущенной загрузки.

### 10.4. Lease

В БД: job_name, lease_owner, lease_until, generation.

- Атомарное получение.
- Конечный срок действия.
- Timeout HTTP короче lease.
- Освобождение с проверкой owner/generation.
- Устаревший исполнитель не пишет после потери права.
- Перед критическими write проверяется fencing token/current generation внутри согласованной БД-операции.
- Истекший lease восстанавливается следующим запуском.
- Сбой не оставляет вечный lock.

### 10.5. API budget

96 запусков в сутки при интервале 15 минут. При 1–3 агрегированных запросах — расчетная нагрузка 96–288 запросов в сутки; это оценка, не суточная квота поставщика.

- Внутренний бюджет <= 8 запросов/мин на общий token.
- Лимитер общий в БД для cron и manual sync.
- Не запрос на каждый матч.
- Фактические вызовы учитывать.
- 429: учитывать Retry-After при наличии, сохранять next_allowed_at.
- Не ждать минуты внутри функции.
- Timeout и ограниченные retries с backoff/jitter.
- 401: ошибка настройки, не бесконечный retry.
- Не дергать внешний API в CI и при каждом build.

### 10.6. Подтверждение результата

Недостаточно наличия счета. Нужны терминальный статус, обе стороны счета, однозначный результат основного времени, отсутствие конфликта.

Политика защиты MVP: одинаковый fingerprint результата на двух успешных наблюдениях, разделенных хотя бы одним интервалом синхронизации. Хранить first_seen/confirmed_at и не считать повторную ручную загрузку через секунду независимым подтверждением. Это снижает риск, но не гарантирует истинность.

### 10.7. Особые случаи

| Случай | Политика |
|---|---|
| До kickoff <= 5 минут | Прием закрыт |
| Kickoff прошел, статус еще scheduled | Прием закрыт |
| Отмена подтверждена | VOID и возврат |
| Перенос до старта | Приостановка, подтвержденный перенос -> возврат по правилам MVP |
| Прерывание | Приостановка, ожидание однозначного итога |
| 48 часов без подтвержденного итога после прерывания | Возврат по опубликованной политике |
| Нет обеих сторон счета | Не рассчитывать |
| Неоднозначный результат | Проверка, без догадки |
| Ошибка API | Сохраненные данные + предупреждение |
| Старые данные > 60 минут | Запрет новых прогнозов |

Значимое изменение kickoff для существующих прогнозов трактовать по явной политике переноса, а не незаметно переоткрывать тот же рынок. В MVP после VOID рынок с уже принятыми прогнозами автоматически не переоткрывается.

### 10.8. Бюджет выполнения

Цель обычного job: 10–30 секунд. Внутренний предел: до 45 секунд с запасом относительно настроенного platform maxDuration. Конкретную конфигурацию проверить на текущем тарифе.

Ограничить размер пачки; остаток продолжит следующий запуск. Никаких бесконечных циклов, незавершаемых запросов и надежды на выполнение detached promise после ответа.

## 13. Безопасность

### 13.1. Доступ и RLS

- RLS и явные grants на всех exposed таблицах.
- Собственные balances/bets/entries видны только владельцу.
- Клиент не пишет wallets, ledger, roles, markets и результаты.
- Публичный рейтинг — безопасный DTO/view/RPC с проверенными правами.
- Не предполагать, что произвольная SQL-view автоматически сохраняет желаемую RLS-семантику: проверить настройки и тестами.
- Роль администратора не берется из редактируемого user metadata.
- Важные проверки есть в endpoint и внутри привилегированных функций.

### 13.2. SQL-функции

По умолчанию SECURITY INVOKER. SECURITY DEFINER только для необходимых ограниченных операций.

Для SECURITY DEFINER:
- SET search_path = '';
- все объекты со схемой;
- минимальные права владельца;
- REVOKE лишний EXECUTE у PUBLIC/anon;
- authenticated получает только явно разрешенные функции;
- проверка auth.uid и аккаунта внутри пользовательской команды;
- расчет/админские функции недоступны обычному пользователю.

Проверить доступ напрямую через Supabase REST/RPC, не только через Next.js. Нельзя считать endpoint единственной точкой входа, если RPC открыт клиентскому ключу.

### 13.3. Секреты и env

```text
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
SUPABASE_SERVICE_ROLE_KEY
FOOTBALL_DATA_API_KEY
CRON_SECRET

```

Точный тип публичного ключа проверить по выбранной версии Supabase. Публичный ключ допустим в клиенте только при корректных grants/RLS. Service-role/API/cron keys — только server-only.

Env validation зависит от режима: demo не требует production credentials. .env.example содержит только имена и фиктивные примеры. Локальные env не коммитить.

Service-role не использовать для всех пользовательских запросов как обход RLS. Серверные привилегированные модули изолировать и пометить server-only.

### 13.4. HTTP и сессия

- Same-origin политика для browser commands, проверка Origin/Host по заданной модели.
- Cookie-параметры по актуальной Supabase SSR схеме.
- Никакого permissive CORS без причины.
- Для cron отдельная машинная аутентификация.
- GET не меняет бизнес-состояние.
- Callback не делает open redirect.
- Middleware не единственная авторизация.
- JSON body ограничен по размеру.
- Все входные поля валидируются.
- CSP/security headers адаптированы к Next.js и OAuth, без слепого копирования ломающих настроек.
- Не рендерить непроверенный HTML.
- Не выполнять SSRF через произвольные avatar/provider URLs.

### 13.5. Rate limiting

Состояние в БД, не памяти функции.

Начальные лимиты:
- place_bet: 10 запросов/мин на пользователя;
- manual sync: 1 запуск/5 минут;
- лимиты чтения выбрать после измерений.

Критический лимит действует и при прямом вызове разрешенного RPC. Идемпотентный повтор не должен создавать повторную бизнес-операцию. Уточнить и протестировать учет повторов, чтобы безопасный сетевой retry не превращался в блокировку без причины.

IP не единственный идентификатор. Не хранить исходные IP бессрочно. Для временных счетчиков использовать минимальный объем данных и TTL.

### 13.6. Зависимости и логи

Dependency audit в CI; не заявлять, что он гарантирует безопасность. Логи без токенов, cookies, заголовков auth, service-role и лишних персональных данных. Утечка -> ротация, аудит, устранение причины; не просто удаление строки из git.

## 14. Скорость, нагрузка и деградация

Цели — измеряемые требования проекта, не обещания бесплатных платформ.

### 14.1. Тестовый профиль

До 50 одновременно активных пользователей, 10 000 прогнозов, 2 000 матчей, несколько соревнований. Не гонять нагрузку без учета квот и условий сервисов. Предпочитать локальную/выделенную тестовую БД.

### 14.2. Целевые показатели

Для прогретого приложения, согласованного региона и описанного профиля:
- список матчей: p95 <= 800 ms;
- приватная история: p95 <= 1000 ms;
- принятие прогноза: p95 <= 1500 ms;
- реакция UI на действие: <= 100 ms;
- мобильный LCP: <= 2.5 s на зафиксированном тестовом профиле.

Cold start измерять отдельно. Отчет содержит окружение, объем данных и фактические результаты, а не только целевые числа.

### 14.3. Кеширование

- Публичные матчи: 30–60 секунд.
- Рейтинг: 60 секунд.
- Баланс/приватная история: без общего публичного кеша.
- Решение о приеме: актуальная транзакционная БД.
- Нельзя кешировать персональную страницу как публичную.

### 14.4. Polling

Видимая вкладка — раз в 60 секунд к собственному API. В фоне пауза, при ошибках backoff, после успешной команды адресная инвалидация. Polling UI не вызывает внешний sports API.

### 14.5. Деградация

API недоступен -> сохраненные данные, stale warning, запрет приема после 60 минут. История/кошелек продолжают работать при доступной БД.

БД недоступна -> понятная ошибка, никакого выдуманного баланса или подтверждения. Не делать автоматический переход с connected на смешанные demo-данные в одном аккаунте.

Различать last_seen_at приложения и provider_updated_at. Не выдавать время загрузки задержанного ответа за время актуальности спортивного события.

## 15. Demo mode и fixtures

### 15.1. Режимы

APP_DATA_MODE=demo: собственные fixtures, без внешних ключей; явная метка; управляемое время; воспроизводимый короткий сценарий.

APP_DATA_MODE=connected: реальные матчи и задержки поставщика, собственные демонстрационные коэффициенты, реальные транзакции виртуальных монет в Supabase.

SPORTS_PROVIDER задает адаптер. Не разрешать противоречивые env-комбинации.

### 15.2. Изоляция

Публичное «попробовать без входа» работает локально в браузере, не пишет в общий рейтинг, не имеет админских прав. Локальное хранилище demo считается недоверенным и не влияет на connected.

Интеграционные тесты используют отдельную локальную БД. Никакого production endpoint «войти любым пользователем». Управление временем/результатами fixtures не доступно для настоящих production-матчей.

Демо может иметь локальный симулятор поведения, но он не заменяет проверку PostgreSQL-транзакций в connected/local integration. Общие чистые доменные правила по возможности переиспользуются.

### 15.3. Обязательные fixtures

- предстоящий матч;
- матч через 3 минуты — прием закрыт;
- победа хозяев;
- победа гостей;
- ничья;
- отмена;
- перенос;
- прерывание;
- null score;
- неоднозначный результат;
- 429;
- timeout;
- изменившийся итог после расчета;
- устаревшие данные;
- частично некорректный ответ.

Фикстуры не протухают через месяц: тестовые часы фиксированы, демонстрационные даты сдвигаются явно.

## 17. План реализации и критерии приемки

### Этап 0. Проверка предпосылок

Задачи:
- проверить актуальные бесплатные условия и документацию;
- при наличии токена выполнить один разрешенный sports запрос;
- выбрать доступные соревнования;
- проверить семантику статусов и основного времени;
- подтвердить схему OAuth, регион и cron;
- зафиксировать ограничения и решения.

Приемка: выбран рабочий путь интеграции; отсутствие ключей не блокирует demo. Не заявлять «интеграция проверена», если есть только код адаптера.

### Этап 1. Каркас и CI

Задачи: Next.js, strict TS, env validation, lint/format, UI shell, страницы ошибок, тестовые инструменты, fixtures, GitHub Actions и preview.

Приемка: на чистом checkout проходят install/lint/typecheck/test/build; demo без секретов открывается на Vercel.

### Этап 2. База и права

Задачи: миграции, FK/checks/indexes, RLS/grants, инициализация кошелька, типы БД, SQL-тесты.

Приемка: reset/replay миграций с нуля; A не читает B; гость не начисляет; прямое изменение wallet запрещено; стартовый кредит однократный, включая конкурентность.

### Этап 3. Auth

Задачи: OAuth, callback, redirect validation, серверная проверка, профиль, protected routes, logout, expired session.

Приемка: localhost и production flow; нет обхода через UI/middleware; потеря сессии не выполняет команду.

### Этап 4. Sports provider

Задачи: адаптеры, DTO validation, normalization, upsert, freshness, rate limit, ошибки и fixtures.

Приемка: нет дубликатов; null/429/timeout покрыты; сохраненные данные работают при недоступном API; CI не требует внешних calls.

### Этап 5. Матчи и рынки

Задачи: каталог, фильтры, timezone, страница матча, коэффициенты, cutoff, stale UI, responsive.

Приемка: детерминированные коэффициенты; неверный матч не открывает рынок; время надежно закрывает прием.

### Этап 6. Прогноз и wallet

Задачи: place_bet, idempotency, locks, купон, история, журнал, конкурентные тесты.

Приемка: нет отрицательного баланса, двойного списания и второго прогноза; журнал совпадает с балансом; повтор после неопределенного сетевого ответа безопасен.

### Этап 7. Расчет и cron

Задачи: подтверждение результата, settlement, refunds, lease, cron, batch/cursor, recovery, аудит.

Приемка: повторный расчет не начисляет снова; сбой возобновляется; устаревший worker не пишет; спорный результат не рассчитывается догадкой.

### Этап 8. Статистика и рейтинг

Задачи: формулы, агрегаты, VOID exclusion, admission threshold, safe DTO, кеш.

Приемка: агрегаты совпадают с проверочным SQL по исходным прогнозам; корректны нулевые случаи и приватность.

### Этап 9. Админка

Задачи: последний успех/ошибка, объем вызовов, backlog, stale, ручной запуск, конфликты.

Приемка: администратор понимает причину задержки конкретного расчета; обычный пользователь не получает эти права через прямой API.

### Этап 10. Hardening

Задачи: полный E2E, SQL/RLS, bundle/query review, нагрузка, accessibility, mobile, секреты в логах, dependency audit.

Приемка: отчет фактических измерений; нет незакрытых критических проблем; ограничения явно описаны.

### Этап 11. Release и портфолио

Задачи: production env/OAuth, контролируемые миграции, smoke, cron, recovery instructions, README, demo script, screenshots/короткое видео, tradeoffs.

Приемка: другой разработчик поднимает проект по инструкции; посетитель проходит сценарий самостоятельно; production не зависит от незадокументированной ручной операции.

Этапы допускают уточнение последовательности при сохранении зависимостей. Не рисовать статистику как выполненную функцию до реализации расчетов и проверки формул.

## 18. Стратегия тестирования

### 18.1. Unit/component

Коэффициенты, нормализация вероятностей, выплата/rounding, исход, market cutoff, timezone/date boundaries, ROI/win rate/VOID, provider normalization, формы и ошибки UI.

### 18.2. SQL/integration

- Однократная инициализация.
- Atomic place_bet и rollback.
- Идемпотентность последовательная и конкурентная.
- Request-hash conflict.
- Прямой RPC обход endpoint.
- RLS/SECURITY DEFINER/EXECUTE.
- Stale/cutoff/disabled account.
- Concurrent placement и settlement.
- Settlement/refund один раз.
- Lease expiry/fencing.
- Job resume и duplicate job.
- Wallet reconciliation.

Ключевой сценарий:
```text
Баланс 1000.
20 конкурентных запросов на разные рынки по 100.
Не более 10 успешных, balance >= 0,
ledger совпадает с wallet, остальные безопасно отклонены.
```

Второй:
```text
10 конкурентных расчетов одного прогноза.
Один terminal transition, одно начисление,
одна соответствующая ledger запись.
```

Третий:
```text
Один idempotency key, два конкурентных запроса.
Одинаковый payload -> один bet, один debit, одинаковый ответ.
Разный payload -> конфликт, без второй операции.
```

### 18.3. E2E

Матчи -> выбор -> подтверждение -> уменьшение баланса -> история -> результат fixtures -> расчет -> журнал -> статистика.

Ошибки: недостаточный баланс, закрытый рынок, stale, expired session, unavailable backend, quote conflict, retry после сетевого сбоя.

OAuth в CI проверять управляемым тестовым контуром. Не создавать production bypass. Отдельно вручную пройти настоящий GitHub OAuth перед release.

### 18.4. CI pipeline

Логические шаги:
1. locked dependency install;
2. formatting/lint;
3. typecheck;
4. unit/component tests;
5. production build в demo env;
6. local Supabase reset + SQL/integration, если runner поддерживает Docker;
7. Playwright;
8. dependency audit по согласованной политике.

Если тяжелые тесты вынесены в отдельный workflow, это не означает их исключение из release gates.

## 19. Vercel deployment и окружения

### 19.1. Окружения

Local: local Supabase + fixtures; sports API опционален.
Preview: demo по умолчанию; без production DB, cron и service-role.
Production: production Supabase + football-data + production cron.

Нельзя использовать production wallet DB для тестов и load test. Secrets разделены. Режим виден в интерфейсе/диагностике.

### 19.2. Порядок release

1. Supabase production и проверка доступности.
2. Контролируемое применение миграций.
3. OAuth provider/callback URLs.
4. Vercel env и регион.
5. Build/deploy.
6. Health + protected smoke.
7. Первая синхронизация.
8. Проверка матчей/рынков.
9. Настройка Supabase Cron и отдельного секрета.
10. Проверка автоматического запуска.
11. Полный smoke пользовательского пути.

Не применять production migrations из Next.js build: preview/parallel deployments не меняют schema.

### 19.3. Регион

Разместить выполнение и БД близко друг к другу в рамках доступных настроек. Выбор — по измеренной function-to-DB latency, а не только близости к пользователю.

### 19.4. Rollback и recovery

Rollback deployment не откатывает БД. Миграции по возможности expand/contract, обратно совместимые. Не удалять поля одновременно с кодом, который еще может быть активен на предыдущем deployment.

Перед рискованной миграцией — проверенный экспорт/backup по доступным возможностям. Не предполагать платные backup/PITR на бесплатном плане. Документировать и хотя бы локально проверить восстановление.

## 20. Наблюдаемость и эксплуатация

### 20.1. Структурированные события

Поля: timestamp, level, event, requestId, jobId, durationMs, providerStatus, processedCount, errorCode. Идентификатор пользователя только по необходимости; минимум PII.

### 20.2. Контроль

- Возраст последней успешной синхронизации.
- Неудачные jobs подряд.
- 429/401 provider.
- Pending backlog и самый старый ожидающий расчет.
- Result conflicts.
- Wallet/ledger mismatch.
- Размер БД и срок хранения job logs.

### 20.3. Runbook минимум

- Provider 401: проверить/ротировать token, не бесконечно retry.
- Provider 429: проверить limiter и next_allowed_at.
- Supabase paused: восстановить доступность, проверить backlog.
- Cron молчит: расписание, URL, секрет, pg_net response, job_runs.
- Задание зависло: lease expiry, owner/generation, безопасный повтор.
- Завершенный матч не рассчитан: status/score/result_kind/confirmation/queue.
- Конфликт итога: ручная проверка, аудит, без тихого overwrite.
- Wallet mismatch: остановить затронутые команды, расследовать журнал, не править сумму без следа.
- OAuth ошибка: callback allowlist, env, provider settings.
- Утечка: ротация, анализ использования, устранение источника и проверка git/logs.

## 24. Журнал архитектурных решений

Начальные решения:
- ADR-001: Next.js + Supabase вместо отдельного постоянно работающего backend, чтобы соответствовать Vercel и масштабу MVP.
- ADR-002: football-data.org как единственный sports provider; задержки видны, коэффициенты собственные.
- ADR-003: single bets only, без cash out/express в MVP.
- ADR-004: балансы и расчеты в SQL-транзакциях; ledger append-only.
- ADR-005: Supabase Cron вызывает ограниченный Vercel job, состояние заданий в PostgreSQL.
- ADR-006: demo изолирован от connected данных и доступен без секретов.
- ADR-007: бесплатность в пределах проверенных квот, без обещания постоянного SLA/нулевой стоимости.

Добавляй новые решения здесь: дата, проблема, решение, альтернативы, последствия. Не удаляй историю без необходимости.

### Решения этапа 0 (2026-10-26)

Проверено по первоисточникам (football-data.org: pricing, coverage, policies, overtime; Vercel: cron, function limits; Supabase: pricing).

- **ADR-008. Соревнования MVP.** Бесплатный тариф football-data: 12 соревнований — Champions League, Primeira Liga, Premier League, Eredivisie, Bundesliga, Ligue 1, Serie A, La Liga, Championship, Brasileirão Série A, World Cup, European Championship. Для MVP выбраны чисто лиговые Premier League, Bundesliga, La Liga (коды PL, BL1, PD — из общеизвестных; **подтвердить запросом с токеном на этапе 4**). Champions League, World Cup и Euro исключены: есть плей-офф и дополнительное время. Альтернатива: добавить кубки после реализации интерпретации основного времени.
- **ADR-009. Основное время.** По документации, `score.fullTime` при `duration = REGULAR` — итог основного времени; при `EXTRA_TIME`/`PENALTY_SHOOTOUT` `fullTime` уже включает дополнительное время и пенальти. Правило: рассчитывать только при `status = FINISHED`, `duration = REGULAR` и обеих сторонах `fullTime`; при другом `duration` брать `regularTime` только если оно непусто, иначе результат неоднозначный (проверка, без догадок). Последствие: для лиг дополнительное время не возникает, но правило остаётся защитой.
- **ADR-010. Выборка матчей.** `GET /v4/matches` без параметров возвращает матчи только за сегодня (UTC). Для синхронизации нужны явные фильтры дат или подресурс соревнования; точные параметры, максимальную длину диапазона и поведение для free-токена **проверить запросом с токеном на этапе 4**. Бюджет: ≤ 8 запросов/мин при лимите провайдера 10/мин.
- **ADR-011. Тулчейн.** Node 22, npm, Next.js 16 (Active LTS; Next.js 15 выходит из поддержки 21.10.2026), React 19, Tailwind 4, Zod 4, Vitest 3, Playwright. Версии заданы диапазонами; lockfile создаётся при первом `npm install` у владельца и коммитится. ### Решения этапа 2 (2026-11-02)

- **ADR-014. Инициализация пользователя.** RPC `public.ensure_user_initialized()` (SECURITY DEFINER, `search_path = ''`, EXECUTE только у `authenticated`) вместо триггера на `auth.users`: функция идемпотентна и вызывается явно из auth-callback (этап 3). Профиль, кошелек и запись `INITIAL_CREDIT` вставляются через `ON CONFLICT DO NOTHING` (без целевого ограничения, чтобы перехватывать и `operation_key`, и частичный уникальный индекс); баланс растет только если запись журнала реально вставлена этим вызовом. Возвращает `(wallet_balance, credited)`. Имя: из OAuth-метаданных, без управляющих символов и `<>`, 3–24 символа, иначе `Аналитик-xxxxxx`; аватар — только https. Отключенный аккаунт получает `ACCOUNT_DISABLED`.
- **ADR-015. Инварианты в БД, а не только в коде.** Журнал append-only (триггер, SQLSTATE 55000). `balance = SUM(wallet_entries.amount)` проверяется отложенным constraint-триггером при COMMIT (23514), поэтому запись журнала и обновление кошелька допустимы в любом порядке внутри транзакции. Принятый прогноз неизменяем, кроме `status/actual_payout/settled_at` из PENDING (55000). `potential_payout = floor(stake * odds / 1000)` — CHECK. CHECK состояний прогноза использует явные `is not null`: CHECK пропускает NULL-результат выражения.
- **ADR-016. Переходы рынка** (триггер, 55000): OPEN → SUSPENDED|CLOSED|VOID; SUSPENDED → OPEN|CLOSED|RESOLVED|VOID; CLOSED → SUSPENDED|RESOLVED|VOID; RESOLVED и VOID терминальны. Переход SUSPENDED → OPEN допущен для снятия ошибочной приостановки; пересмотреть на этапах 5 и 7.
- **ADR-017. Права по умолчанию отозваны.** У `anon` и `authenticated` отозваны все права на таблицы и функции схемы `public`, а также default privileges; клиентам явно выданы только SELECT на публичные спортивные данные, SELECT на собственные приватные данные и UPDATE(display_name) профиля. Для функций PUBLIC-EXECUTE Postgres выдает всегда, поэтому каждая новая функция обязана делать `REVOKE ... FROM PUBLIC`. Запись в `wallets`, `wallet_entries`, `bets`, `markets`, `matches`, `user_roles` у клиентов отсутствует.
- **ADR-018. Поэтапное создание таблиц.** Служебные таблицы (`job_runs`, `job_leases`, `sync_cursors`, `provider_rate_limits`, `audit_events`, `rate_limit_buckets`, `user_stats`) создаются на этапах 7–9 expand-only миграциями. Внешние ключи без каскадного удаления: удаление аккаунта потребует отдельной процедуры обезличивания.
- **Отложено:** генерация типов БД (`supabase gen types`). В Windows PowerShell 5 оператор `>` пишет файл в UTF-16, поэтому вывод нужно сохранять через `Out-File -Encoding utf8` или Node-скрипт; сделать в начале этапа 3, когда код впервые обратится к БД.

### Решения этапа 5 (2026-11-04)

- **ADR-029. Демонстрационные коэффициенты.** `computeDemoOdds(provider, providerMatchId, modelVersion)`: SHA-256 от ключа → три равномерных числа → веса (хозяева 0.30–0.70, ничья 0.20–0.32, гости 0.20–0.60) → нормализация → ограничение вероятностей с сохранением суммы 1 → `floor(1000 / (p × 1.06))`. Ключ — ID поставщика, а не внутренний UUID, поэтому значения переживают пересоздание БД. Итог матча не используется. Значения считаются на сервере при создании рынка и фиксируются в БД (`model_version = demo-v1`, `quote_version = 1`); изменение алгоритма требует новой версии модели (в тестах закреплены эталонные значения). На 20 000 матчей диапазон фактически 1.50–6.90, маржа 6.0–7.5%. Если коэффициенты не прошли проверку — рынок не открывается.
- **ADR-030. Решение о приеме — функция времени, а не задания.** `acceptanceState` (домен) закрывает прием, если рынок не OPEN, матч не SCHEDULED, до старта ≤ 5 минут или данные старше 60 минут (`last_seen_at`). Время берется из часов PostgreSQL (`db_now` витрины), в демо — фиксированное `DEMO_NOW`. Поэтому рынок, который синхронизация еще не закрыла, все равно не принимает прогнозы. Окончательная проверка — в `place_bet` (этап 6) по тем же правилам.
- **ADR-031. Обслуживание рынков в синхронизации.** После загрузки матчей (и даже если поставщик недоступен) `sync_close_markets()` приостанавливает рынки перенесенных/прерванных/отмененных матчей и закрывает рынки с истекшим сроком или начавшихся/завершенных матчей; приостановленный рынок доигранного матча закрывается для расчета. Автоматического переоткрытия нет. Отмена в этапе 5 только приостанавливает рынок: VOID с возвратом ставок делает расчет (этап 7). Затем `sync_matches_needing_market` + `sync_create_markets` создают недостающие рынки (ON CONFLICT DO NOTHING, повторная проверка времени по часам БД). Все три функции — только `service_role`.
- **ADR-032. Каталог.** Витрина `public.match_catalog` (security_invoker, только включенные соревнования) и функция `list_matches` (фильтры: поставщик, соревнование, интервал UTC, scope; курсор `(kickoff_at, id)`; возвращает limit + 1 строку как признак следующей страницы). Одна серверная реализация для страниц и `GET /api/v1/matches[/:id]`; в демо — тот же контракт поверх fixtures. Публичный API кешируется на 30 с (`s-maxage=30`).
- **ADR-033. Часовой пояс.** Фильтр даты — сутки в выбранной зоне, переведенные в интервал UTC (учитываются сутки 23/25 часов при переходе на летнее время). Зона выбирается в форме (по умолчанию подставляется зона браузера); без явной зоны время показывается в зоне браузера, а фильтр даты считается в UTC — это написано на странице.

### Решения этапа 6 (2026-11-04)

- **ADR-034. place_bet в одной транзакции.** SECURITY DEFINER, `search_path = ''`, EXECUTE только у `authenticated`. Порядок: пользователь из `auth.uid()` → проверка полей → аккаунт (не отключен) → повтор по ключу → лимит частоты → рынок FOR SHARE → матч FOR SHARE → условия приема по часам БД (рынок OPEN, матч SCHEDULED, лига включена, до старта > 5 мин, `last_seen_at` не старше 60 мин) → `quote_version` → кошелек FOR UPDATE → повторная проверка ключа и «уже есть прогноз» → баланс → bet + STAKE_DEBIT (`operation_key = stake:<bet_id>`) + обновление кошелька. Коэффициент и выплата берутся из БД; клиентские userId/odds/payout/balance схема API отклоняет.
- **ADR-035. Бизнес-отказы — ответом, а не исключением.** `place_bet` возвращает `{ok:false, code}`: транзакция фиксируется, и счетчик частоты учитывает отклоненную попытку. Исключения — только для неожиданных ошибок; API превращает их в 503 без деталей. Коды → HTTP по §11.2; добавлен `ACCOUNT_NOT_READY` (409) для пользователя без профиля/кошелька.
- **ADR-036. Идемпотентность.** `request_hash = md5(market|outcome|stake|quote_version)`. Повтор ключа с тем же отпечатком возвращает исходный прогноз (`replay: true`, HTTP 200 вместо 201), даже если рынок уже закрыт, и не расходует лимит. Другой отпечаток — `IDEMPOTENCY_CONFLICT`. Конкурентные запросы одного пользователя сериализуются на строке кошелька (и счетчика частоты), после блокировки ключ проверяется заново; уникальные ограничения `(user_id, idempotency_key)` и `(user_id, market_id)` — последняя линия защиты. Клиент держит один ключ на намерение: после сетевой ошибки повторяет его, при смене исхода/суммы или после отказа по существу создает новый.
- **ADR-037. Порядок блокировок.** `rate_limit_buckets → markets → matches → bets → wallets` (комментарий в миграции 20261106000001). Расчет и возвраты (этап 7) обязаны следовать ему: рынок FOR UPDATE, затем прогнозы, затем кошельки по возрастанию user_id.
- **ADR-038. Лимит частоты.** `rate_limit_buckets` (ключ `place_bet:<user_id>`, окно 60 с, 10 попыток), функция `rate_limit_hit` недоступна клиентам и вызывается внутри `place_bet`, поэтому действует и при прямом вызове RPC. IP не используется. Очистка старых строк — этап 7.
- **ADR-039. История.** Витрина `bet_history` (security_invoker: RLS `bets` оставляет только свои) и `list_my_bets` (курсор `(created_at, id)`, новые сверху, фильтр статуса). Страница `/my/bets`, API `GET /api/v1/me/bets`. В демо-режиме прогнозы не принимаются (POST → 503), купон не показывается.
- **ADR-040. «Вошел» = есть профиль.** Подписанный токен не гарантирует существование аккаунта: после удаления пользователя (в т. ч. `db:reset` локально) или сбоя инициализации старая cookie остается валидной. Страница `/login` перенаправляет дальше только при наличии профиля; иначе показывает вход, и новый вход заменяет устаревшую сессию. Найдено владельцем: в старом браузере вход «перебрасывал на главную».
- **ADR-041. Каталог по умолчанию — «Можно сделать прогноз».** По просьбе владельца `/matches` без параметров показывает только матчи с открытым рынком, статусом SCHEDULED и запасом > 5 минут (по часам БД); «Все предстоящие», «Завершённые» и «Все» — в фильтре. Матчи с устаревшими данными в этой области остаются видимыми с предупреждением (состояние временное, place_bet все равно откажет). Изменение `list_matches` — новой миграцией 20261107000001 (примененные миграции не правятся).

### Решения этапа 7 (2026-11-04)

- **ADR-042. Подтверждение итога — два одинаковых наблюдения с интервалом ≥ 10 минут.** Отпечаток итога (`FINISHED:h:a`, `CANCELLED`, `POSTPONED`) сохраняется при первом наблюдении; `result_confirmed_at` ставится, когда тот же отпечаток виден снова не раньше чем через 600 с. AMBIGUOUS и иные состояния не подтверждаются и не рассчитываются автоматически.
- **ADR-043. Расчет: WON/LOST по основному времени, VOID при подтвержденной отмене/переносе и SUSPENDED > 48 ч.** `settle_market` в одной транзакции блокирует рынок, матч (FOR SHARE), прогнозы и кошельки в порядке `user_id`; выплаты и возвраты — записи журнала с ключами `win:<bet>` / `refund:<bet>`, поэтому повторный расчет ничего не начисляет. Рынок не в статусе CLOSED/SUSPENDED пропускается (SKIPPED).
- **ADR-044. Изменение итога после расчета не переписывает историю.** Если подтвержденный отпечаток меняется у рассчитанного (RESOLVED) рынка — `result_conflict_at`, одна запись `RESULT_CHANGED_AFTER_SETTLEMENT` в `audit_events`, матч исключается из автоматики до `admin_ack_result_conflict`. Исправление денег — только `admin_compensate` (новая запись журнала, уникальный ключ, баланс не уходит в минус). Изменение VOID-рынка (отмена → перенос) конфликтом не считается.
- **ADR-045. Аренда задания с fencing по поколению.** `job_leases(job_name, lease_owner, lease_until, generation)`; захват увеличивает поколение; `settle_ready_markets` перед каждым рынком вызывает `job_assert_lease` (FOR SHARE), и исполнитель с устаревшим поколением получает `LEASE_LOST` без записей. Аренда 120 с, пачка 50 рынков, ошибка одного рынка — аудит `SETTLEMENT_FAILED`, остальные продолжаются. `settle_market` не исполняется ни одной ролью напрямую.
- **ADR-046. Один конвейер на запуск, журнал `job_runs`.** `POST /api/internal/jobs/sync`: синхронизация → рынки → подтверждение → расчет → очистка; каждый шаг изолирован, итог OK/PARTIAL/SKIPPED/FAILED записывается в `job_runs`. Очистка: корзины лимитов старше суток, `job_runs` старше 30 дней.
- **ADR-047. Cron — шаблон SQL, а не миграция.** `supabase/cron/schedule-sync.sql` (pg_cron + pg_net, адрес и секрет в Vault) выполняется вручную в облачном проекте: миграции не должны содержать адрес развертывания и секреты, а локальная база не должна вызывать production.

### Решения этапа 8 (2026-11-05)

- **ADR-048. Статистика считается по `bets`, а не по журналу.** WON/LOST — основной расчет; VOID и PENDING показываются отдельно и не входят в win rate, ROI и прибыль; INITIAL_CREDIT и ADMIN_ADJUSTMENT в прибыль не попадают по построению. БД возвращает только счетчики и суммы (`my_stats`, SECURITY INVOKER + RLS), проценты считаются одной чистой функцией `summarize` (нулевой знаменатель → «—»).
- **ADR-049. Рейтинг — SECURITY DEFINER с безопасным DTO.** Внутренняя `leaderboard_ranked()` (с user_id) не выдана ни одной роли; публичная `leaderboard(limit 1..100)` возвращает место, имя, аватар и агрегаты; `my_leaderboard_place()` — место текущего пользователя. Допуск ≥ 5 рассчитанных, отключенные профили скрыты, сортировка net_profit ↓, settled ↓, user_id. Места уникальные (row_number), не «общие».
- **ADR-050. Кеш рейтинга 60 секунд.** Ответ одинаков для всех, поэтому кешируется в памяти экземпляра (TTL, одновременные промахи делят запрос, ошибки не кешируются) и в CDN (`s-maxage=60`). Место пользователя запрашивается отдельно и не кешируется. Кеш в памяти — на экземпляр функции; согласованность между экземплярами не требуется.
- **ADR-051. Демо-рейтинг из вымышленных игроков.** В demo `/leaderboard` строится той же `rankPlayers` из fixtures с явной пометкой «демонстрационные данные»; демо-прогнозы туда не пишутся.

### Решения этапа 9 (2026-11-05)

- **ADR-052. Роль администратора проверяется в БД при каждом запросе.** `is_admin()` читает только `user_roles` (не профиль и не user metadata) и учитывает `disabled_at`. Все админ-функции — SECURITY DEFINER с `admin_assert()` внутри: прямой вызов через PostgREST обычным пользователем → 42501 FORBIDDEN, гостю EXECUTE не выдан. Страница `/admin` не администратору и в demo отвечает 404 (раздел не раскрывается); API — 401/403/404 по контракту.
- **ADR-053. Причина ожидания расчета вычисляется в БД.** `settlement_wait_reason` повторяет ветвления `settle_market` (конфликт, рынок открыт, матч не завершен, прерван < 48 ч, неоднозначный итог, нет счета, ждет подтверждения, готов) — pgTAP сверяет причины с фактическим результатом `settle_market`. Очередь включает и матчи с конфликтом, у которых рынок уже рассчитан. Пояснение и ожидаемое время — чистая функция `explainWait`.
- **ADR-054. Ручной запуск — тот же конвейер под той же арендой.** `admin_request_sync()` проверяет роль, ограничивает запуск одним в минуту на всех администраторов и пишет аудит с автором; затем сервер выполняет `executeSyncJob` (общий с cron). Параллельный cron получает SKIPPED/LEASE_HELD. Привилегированный клиент используется только после проверки роли.
- **ADR-055. Снятие конфликта из админки — с причиной и автором.** `admin_resolve_conflict` вызывает `admin_ack_result_conflict` (прямо пользователю не выдана) и пишет `ADMIN_CONFLICT_RESOLVED` с user_id. Компенсации остаются в SQL владельца (runbook): денежные операции не выносятся в веб-интерфейс MVP.

### Решения этапа 10 (2026-11-05)

- **ADR-056. CSP с nonce в proxy.ts.** `script-src 'self' 'nonce-…' 'strict-dynamic'` (в dev + `'unsafe-eval'`), `style-src 'self' 'unsafe-inline'` (style-атрибуты Next/React; внешних стилей нет), `form-action 'self'` + origin Supabase + github.com (браузер проверяет цепочку редиректов входа), `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`. Nonce свой у каждого ответа, поэтому RootLayout вызывает `connection()` и все страницы рендерятся динамически (статической предварительной отрисовки нет — осознанная цена). e2e проверяет заголовок и отсутствие нарушений CSP на ключевых страницах.
- **ADR-057. Ручной запуск — 1 раз в 5 минут (§13.5).** В этапе 9 был 1/мин — расхождение с контекстом найдено при ревью; исправлено новой миграцией 20261111000001 (`create or replace`), ADR-054 в остальном в силе.
- **ADR-058. Логи очищаются в одном месте.** `logEvent` заменяет значения чувствительных полей (token, secret, password, authorization, cookie, api key, service role, email, jwt) на `[redacted]`, вычищает bearer-токены, JWT и email внутри строк, обрезает длинные строки и глубину. verify.ps1 дополнительно ищет значения секретов из `.env.local` в логах локальных серверов (значения не печатаются).
- **ADR-059. Лимиты чтения не вводятся до облачных измерений.** §13.5 требует выбирать их после измерений; локальные числа (docs/measurements.md) не отражают сеть и холодные старты Vercel. Публичные чтения защищены кешем (матчи 30 с, рейтинг 60 с, CDN `s-maxage`). Вернуться на этапе 11 по облачным метрикам.
- **ADR-060. Измерения — скрипт, а не разовые цифры.** `scripts/perf/measure.mjs` (запуск `verify.ps1 -Measure`) создает в локальной БД профиль §14.1 под поставщиком `perf`, меряет функции БД под ролями anon/authenticated, HTTP p50/p95 к `next start`, холодный старт и мобильный LCP (Pixel 5, 360 px, CPU ×4, медленный 4G). Результат — `.verify/perf.json`, сводка с окружением — docs/measurements.md.
